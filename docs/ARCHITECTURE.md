# Envo Desk — архитектура автономного мониторинга продаж для macOS

Цель: всё, что сейчас крутится в Cowork-рутинах через Claude, должно работать само —
как обычная программа на Mac, без сессий, без токенов, без «а вдруг у контейнера нет сети».
Claude остаётся опциональным помощником для задач с суждением (анализ спроса, копирайт),
а не обязательным звеном в операционном цикле.

---

## 1. Что переносим: инвентарь текущих задач

| Рутина (Cowork) | Период | Что делает | От чего зависит |
|---|---|---|---|
| `Envo · продажи, письма и отчёты` | каждый час | тянет заказы из CRM Яндекс.Афиши, пишет новые билеты в Google Sheets (лист на событие), ловит возвраты, формирует вэлком-письма, проверяет в Outlook «не писали ли раньше», отправляет с support@envo.live, отмечает отправку, шлёт отчёт в Telegram; в 06:00 и 15:00 UTC — сводки за утро и за день | CRM API, Apps Script + Sheets, коннектор Microsoft 365, Telegram Bot API, Claude как исполнитель шагов 3–4 |
| `Envo · догон брошенных корзин` | каждые 2 часа | находит незавершённые заказы (`status=0`) за 30 дней, фильтрует (≤4 билетов, ≥7 дней до события, событие в трекинге, карантин, дедуп по e-mail), отправляет письмо со скидкой 10%, ведёт статусы корзин в Sheets, окно отправки 09:00–21:00 МСК, потолок 10 писем за прогон | то же + отдельные листы корзин |
| `Envo · лестница цен UFC 333, кат. 6` | каждые 2 часа | считает проданное по каждой ценовой ступени (94 500 / 108 000 / 126 000 ₽, квоты 7/17/9), сверяет со счётчиками в Sheets `meta`, при закрытии ступени шлёт в Telegram «ставь следующую цену», ловит продажи мимо лестницы | CRM API, Sheets meta, Telegram |
| `Envo · тест сети` | вручную | проверяет, видит ли облако три домена | — |
| Навык `resale-pricing` | по запросу | курс ЦБ +1 ₽, модель цены (Афиша 6%, налоги 12%, отправка 0,9%, волны 30/40/50%, витрина `P/0.9`, возвратный +15–20%), xlsx, рекомендации по закупке | скрипты навыка, веб-поиск для оценки спроса |

Плюс неавтоматизированное, но живущее в тех же данных: справочник событий (отображаемое
имя, тексты писем single/multi, флаг трекинга), статусы корзин (ответил / отправили ссылку /
результат), ручные решения по докупке.

## 2. Где сейчас больно (и что из этого чинит архитектура)

1. **Логика живёт в тексте промпта.** Скрипт `envo_min.py` (~400 строк) целиком вложен в
   рутину и переписывается на диск при каждом запуске. Любая правка — правка промпта;
   версий нет, откатиться некуда, diff не посмотреть.
2. **Сеть.** Облачному контейнеру недоступны `api.tickets.yandex.net`, `script.google.com`,
   `api.telegram.org` — отсюда дубль рутины «на компьютере» через `device_bash`. Mac своей
   сетью решает это полностью.
3. **LLM в критическом пути.** Отправка писем, проверка «писали ли раньше», отметка
   `mark-sent` — шаги, которые выполняет модель. Это источник недетерминизма в операции,
   где нужна ровно одна попытка и точная идемпотентность.
4. **Секреты в открытом виде.** Пароль CRM, shared secret Apps Script, токен Telegram-бота
   лежат текстом внутри промптов рутин. **Их нужно ротировать при миграции** — считать их
   скомпрометированными. В новой схеме они живут только в Keychain.
5. **Реакция медленная из-за цены прогона.** Лестница цен проверяется раз в 2 часа, продажи —
   раз в час, потому что каждый прогон — сессия модели. Локальная программа может опрашивать
   CRM каждые 5–10 минут бесплатно; ступень будет закрываться почти в реальном времени.
6. **Состояние в Google Sheets.** Sheets как база: нет транзакций, нет уникальных ключей,
   дедуп держится на соглашениях (`order:ticketId`), запись идёт через Apps Script с общим
   секретом. Годится как витрина, не годится как источник истины.
7. **Потолки из-за коннектора.** 5 писем за 5 минут — ограничение коннектора, а не почты.

## 3. Целевая картина

Одно приложение: **детерминированное ядро** (вся логика, порты существующих скриптов),
**локальная БД SQLite** как источник истины, **планировщик** с догоном пропущенных запусков,
**очередь исходящих писем** с ручным или авто-подтверждением, и **UI в меню-баре + окно**
для того, что сегодня делается руками в Sheets.

```
┌──────────────────────── Envo Desk.app (macOS, Swift) ─────────────────────────┐
│  SwiftUI UI: меню-бар · Дашборд · Журнал продаж · Корзины · Аутбокс ·         │
│              Справочник событий · Лестницы цен · Калькулятор цены · Настройки │
├───────────────────────────────────────────────────────────────────────────────┤
│  Scheduler (jobs, cron-spec, catch-up после сна, одна копия задачи)           │
├───────────────────────────────────────────────────────────────────────────────┤
│  Пайплайны:  SalesSync │ CartsPipeline │ LadderMonitor │ Digests │ Pricing    │
├───────────────────────────────────────────────────────────────────────────────┤
│  Сервисы:  CRMClient │ Mailer(Graph) │ Notifier(TG+macOS) │ SheetsExport │    │
│            RatesClient(ЦБ) │ Templates │ Secrets(Keychain) │ Store(SQLite)    │
└───────────────────────────────────────────────────────────────────────────────┘
        │                 │                │              │            │
   CRM Афиши        Microsoft Graph    Telegram      Google Sheets    cbr.ru
  (заказы, билеты)   (отправка, sent)   (алерты)     (витрина, опц.)  (курсы)
```

Тот же код собирается как `envoctl` — консольный бинарник без UI. Нужен для отладки, cron и
для варианта «движок на сервере, Mac — только интерфейс» (см. §11).

## 4. Стек: Swift + SwiftUI, одна сборка

**Рекомендация: Swift (ядро — SPM-пакет `EnvoCore`, UI — SwiftUI, БД — SQLite через GRDB).**

Почему:
- один подписанный бинарник, никакого Python-рантайма внутри `.app`, нет venv и дрейфа
  зависимостей — это главная статья долгосрочной поддержки;
- родные вещи из коробки: Keychain, launchd, уведомления, автозапуск, App Sandbox;
- `URLSession` + `Codable` закрывают 90% кода (всё внешнее — это HTTP + JSON);
- ядро собирается и под Linux (Foundation + GRDB), то есть при необходимости переезжает на
  VPS без переписывания.

Отвергнутые варианты:
- **Python + PyInstaller/rumps.** Быстрее стартовать (код уже есть), но дальше — боль с
  нотаризацией, arm64, обновлением зависимостей, и всё равно два языка в проекте.
- **Electron/Tauri.** Смысл только если нужен общий UI с вебом. Не нужен.
- **Чистый launchd + набор скриптов без UI.** Дешевле всего, но справочник, аутбокс и
  журнал всё равно придётся где-то редактировать — тогда мы просто остаёмся в Sheets.

Существующий Python при этом не выбрасываем: он — **эталон поведения**. На фазе переноса
гоняем старый скрипт и новое ядро параллельно и сверяем выводы (см. §13).

## 5. Модули ядра

```
EnvoCore/
  Sources/
    CRMClient/        — подпись sha1(md5(pass)+ts), actions, ретраи с backoff, нормализация
                        ответов (CRM отдаёт то объект, то массив), пул запросов, троттлинг
    Store/            — GRDB: схема, миграции, транзакции, upsert'ы, курсоры
    SalesSync/        — новые билеты, возвраты, постановка писем в очередь
    CartsPipeline/    — машина состояний корзины: новая → карантин → готова → отправлено
                        → ответил → купил / исключена
    LadderMonitor/    — ступени по событию+категории, счётчики, алерты, продажи мимо лестницы
    Digests/          — утренняя и дневная сводка, формат как сейчас (Дубай, UTC+4)
    Pricing/          — порт price_model.py: волны маржи, «красивое» округление, возвратный,
                        xlsx-экспорт, курс ЦБ +1 ₽
    Mailer/           — Microsoft Graph: OAuth2, sendMail, поиск в «Отправленных»,
                        rate limiter, dry-run
    Templates/        — письма (вэлком single/multi, догон корзины), обращение по имени
                        (порт GIVEN/STRONG/WEAK-эвристики), склонение числительных
    Notifier/         — Telegram Bot API + UNUserNotificationCenter, дедуп и анти-спам
    SheetsExport/     — необязательное зеркало в Google Sheets (чтение справочника на фазе 1)
    Scheduler/        — job registry, cron-spec, catch-up, блокировка «одна копия»
    Secrets/          — Keychain, никаких секретов в коде и конфиге
```

Интерфейсы — узкие и тестируемые, все внешние вызовы за протоколом:

```swift
protocol CRMAPI {
    func events() async throws -> [CRMEvent]
    func agents() async throws -> [CRMAgent]
    func orders(from: Date, to: Date) async throws -> [CRMOrder]
    func orderInfo(id: String) async throws -> CRMOrderInfo
}

protocol MailSender {
    func send(_ m: OutgoingMail) async throws -> MailReceipt     // provider message id
    func alreadySent(matching: String) async throws -> Bool      // страховка по sentItems
}

protocol Job {                       // всё, что в планировщике
    var id: String { get }           // "sales.sync", "carts.scan", "ladder.check"
    var schedule: Schedule { get }
    func run(_ ctx: RunContext) async throws -> JobResult
}
```

## 6. Модель данных (SQLite)

Источник истины — локальная база. Sheets, если остаётся, становится производной витриной.

```sql
events(id, crm_id UNIQUE, name, display_name, starts_at, venue,
       tracking INT DEFAULT 1, letter_single TEXT, letter_multi TEXT, updated_at)

orders(crm_id TEXT PRIMARY KEY, event_id, status INT, is_returned INT,
       customer_name, salutation, email, phone, agent_id, showcase,
       ordered_at, total_rub, tickets_count,
       first_seen_at, last_seen_at, raw_json)

tickets(order_crm_id, ticket_id, barcode, sector, price_rub, sold_at, status,
        PRIMARY KEY (order_crm_id, ticket_id))          -- ключ дедупа как сейчас

carts(crm_id TEXT PRIMARY KEY, event_id, email, phone, customer_name, salutation,
      tickets_count, total_rub, discount_rub, state, quarantine_until,
      letter_sent_at, replied_at, link_sent_at, result, updated_at)

emails(id, kind, ref_id, to_addr, subject, body_html, body_hash,
       state,                       -- queued | held | sent | failed | skipped
       provider_message_id, created_at, sent_at, attempts, last_error,
       UNIQUE (kind, ref_id))       -- жёсткая гарантия «одно письмо на заказ/корзину»

ladders(id, event_id, category_match TEXT, active INT, count_from DATE)
ladder_steps(ladder_id, idx, our_price_rub, quota, label, sold, closed_at,
             PRIMARY KEY (ladder_id, idx))

runs(id, job_id, started_at, finished_at, status, stats_json, error)
kv(key PRIMARY KEY, value)          -- метки сводок, курсоры, lastRun
audit(id, at, actor, action, payload_json)
```

Главное отличие от Sheets: `emails(kind, ref_id)` — **уникальный индекс**. Повторное письмо
по заказу физически невозможно, а не «не должно случиться по логике промпта». То же для
`tickets` — запись билета идемпотентна.

## 7. Планировщик и надёжность

- **Задачи и период** (период теперь выбирается из смысла, а не из цены прогона):
  `sales.sync` — 10 мин · `ladder.check` — 10 мин · `carts.scan` — 30 мин ·
  `mail.dispatch` — 2 мин (дренаж очереди) · `digest.morning` 06:00 UTC ·
  `digest.evening` 15:00 UTC · `rates.fetch` — раз в сутки · `sheets.export` — раз в час ·
  `heartbeat` — 15 мин.
- **Догон после сна.** У каждой задачи хранится `lastSuccessAt`. При пробуждении Mac
  (`NSWorkspace.didWakeNotification`) планировщик считает, что просрочено, и выполняет —
  один раз, не по разу за каждый пропущенный слот.
- **Идемпотентность везде.** Окно сканирования продаж — 3 дня (как сейчас `WINDOW=3`),
  корзин — 30 дней; повторная обработка тех же заказов ничего не меняет.
- **Одна копия задачи.** Блокировка в БД + `flock` на файле, чтобы ручной запуск из UI не
  пересёкся с расписанием.
- **Окна тишины и потолки** переносятся как конфиг, а не как константы в коде:
  окно отправки догона 09:00–21:00 МСК, карантин корзины, ≤4 билетов, ≥7 дней до события,
  потолок писем за прогон, темп отправки.
- **Kill switch.** Глобальный тумблер «не отправлять ничего» в меню-баре; при включении
  письма остаются в аутбоксе со статусом `held`.
- **Бэкап.** Ежедневный `VACUUM INTO` в `~/Library/Application Support/EnvoDesk/backups/`
  + копия в iCloud/внешний диск. База — единственное, что нельзя потерять.

## 8. Интеграции

**CRM Яндекс.Афиши.** Тот же протокол, что в текущих скриптах: `auth = login:sha1(md5(pass)+ts):ts`,
`city_id`, actions `crm.event.list`, `crm.agent.list`, `crm.order.list`, `crm.order.info`.
Узкое место — `order.info` на каждый заказ; кэшируем по `crm_id` + `last_seen_at` и
перезапрашиваем только изменившиеся. Ответы складываем в `raw_json`, чтобы при изменении
формата можно было переразобрать историю без повторного обхода API.

**Почта — Microsoft Graph (рекомендуется).** Регистрация приложения в Entra ID, delegated
`Mail.Send` + `Mail.Read`, OAuth2 device-code при первом входе, refresh-токен в Keychain,
отправка `POST /v1.0/me/sendMail` от support@envo.live. Плюсы против коннектора: письма
попадают в «Отправленные», нет потолка 5/5мин (только лимиты Graph), проверка «писали ли
раньше» — обычный поиск по `sentItems`, а не шаг модели.
*Фоллбэк:* SMTP (`smtp.office365.com:587`) — проще, но требует включённого SMTP AUTH для
ящика и не даёт чтения «Отправленных»; тогда дедуп держится только на локальной таблице
`emails`. Отдельно проверить SPF/DKIM/DMARC для `envo.live` — письма с благодарностями и
скидками легко уезжают в спам.

**Telegram.** Остаётся как мобильный канал — он работает и привычен. Добавляется:
группировка алертов, анти-дубль, и inline-кнопки для действий («отправить письма»,
«перевести лестницу на следующую ступень») — тогда подтверждение делается с телефона.

**Google Sheets.** На фазе 1 — продолжаем читать справочник через тот же Apps Script, чтобы
ничего не ломать. На фазе 5 справочник переезжает в UI, а Sheets остаётся витриной
только для записи (экспорт журнала и сводок), либо отключается совсем.

**Курсы ЦБ.** Порт `fetch_rates.py`: `cbr.ru/scripts/XML_daily.asp`, кросс-курс, +1 ₽ буфер,
USD/RUB для перевода прибыли. Кэш на сутки в `kv`.

## 9. UI приложения

Меню-бар (`LSUIElement`, иконка + бейдж): продажи за сегодня, сколько писем ждёт,
статус лестниц, «Запустить сейчас», kill switch.

Окно:
1. **Дашборд** — билеты/заказы/выручка за сутки и за 7 дней, возвраты, разбивка по событиям,
   последние продажи лентой, состояние задач (когда последний успешный прогон).
2. **Журнал продаж** — то, что сейчас листы Sheets: таблица с фильтрами по событию, витрине,
   статусу; экспорт в xlsx/csv.
3. **Корзины** — колонки по состояниям, видно сумму, скидку, что отправлено, что ответили.
4. **Аутбокс** — очередь писем с предпросмотром HTML; кнопки «Отправить», «Отложить»,
   «Никогда»; тумблер авто-отправки по типу письма.
5. **Справочник событий** — отображаемое имя, трекинг, тексты писем single/multi
   (с подстановкой переменных и предпросмотром).
6. **Лестницы цен** — ступени, квоты, сколько продано, цена у нас и на витрине Афиши
   (`price/0.9`); лестница создаётся для любого события и категории, а не прошита в коде.
7. **Калькулятор цены** — входные данные как в навыке (валюта, сборы продавца, категории),
   на выходе таблицы по волнам, витрина, xlsx.
8. **Настройки** — ключи (Keychain), расписания, окна тишины, потолки, каналы уведомлений.
9. **Журнал прогонов** — что делала программа, с ошибками и диффами.

## 10. Секреты и безопасность

- Всё — в Keychain (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`), в коде и конфиге нет
  ни одного секрета; конфиг-файл — только неконфиденциальные настройки.
- **Ротировать при миграции:** пароль CRM `Maslov_crm_api`, shared secret Apps Script,
  токен Telegram-бота. Сейчас они лежат текстом в промптах рутин — это значит, что они
  прошли через логи сессий и историю чатов.
- Apps Script webhook после ротации секрета ограничить ещё и по действиям (только те,
  что реально нужны).
- База нешифрованная, но лежит в `~/Library/Application Support` при включённом FileVault;
  если нужно жёстче — SQLCipher.
- Бэкапы с персональными данными покупателей (имена, телефоны, e-mail) — только на
  зашифрованные носители. В репозиторий база и бэкапы не попадают (`.gitignore`).
- `audit` пишет, кто и что отправил — включая ручные действия из UI.

## 11. Где это крутится 24/7 — единственный настоящий риск Mac-приложения

Ноутбук спит. Для часового мониторинга это главная слабость, и её надо закрыть осознанно:

- **Вариант А (рекомендую для старта): Mac всегда в сети и не спит.** Питание от сети,
  «Запрет автоматического сна» при подключённом адаптере, `pmset repeat wakeorpoweron`
  как страховка, догон пропущенных запусков в планировщике. Дёшево, работает, если машина
  стоит дома/в офисе включённой.
- **Вариант Б: отдельный Mac mini** как всегда-включённый узел. Тот же `.app`, никаких
  изменений в коде.
- **Вариант В: движок на маленьком Linux-VPS, Mac — только UI.** Поэтому ядро и пишется
  кросс-платформенным: `envoctl` под systemd на VPS, БД там же, приложение на Mac
  подключается к ней по SSH-туннелю/простому HTTP API. Это единственный вариант с честными
  99,9% и независимостью от того, открыт ли ноутбук. Переход возможен в любой момент
  после фазы 2 — без переписывания логики.

Мой совет: строить по варианту А, но не закладывать в код ничего, что мешает переезду на В
(никакой логики в UI-слое, никаких путей macOS внутри ядра).

## 12. Наблюдаемость

- Структурные логи в файл с ротацией + просмотр в UI.
- Таблица `runs` — длительность, статистика, ошибки каждого прогона.
- **Dead man's switch:** после каждого успешного прогона — пинг во внешний сервис
  (healthchecks.io или аналог). Если Mac уснул/программа упала, сигнал приходит от внешнего
  сервиса, а не ожидается от упавшей программы. Это критично: молчание Telegram сейчас
  неотличимо от «нет продаж».
- Раз в сутки короткий статус в Telegram: прогонов N из ожидаемых M, ошибок K.
- Алерты об ошибках с подавлением повторов (одна и та же ошибка — не чаще раза в час).

## 13. Миграция по фазам

Принцип: ни одну рутину не отключаем, пока новая реализация не отработала параллельно и
не совпала с ней по выводу.

| Фаза | Объём | Критерий готовности | Что выключаем в Cowork |
|---|---|---|---|
| **0. Каркас** | репозиторий, `EnvoCore`, схема БД, Keychain, `envoctl`, CRMClient только на чтение, ингест заказов/билетов в SQLite | данные за 30 дней в базе совпадают с листами Sheets (скрипт сверки) | — (плюс: ротация секретов) |
| **1. Лестница цен** | `LadderMonitor` + Telegram, ступени из UI, период 10 мин | сутки параллельной работы: те же счётчики, те же алерты | рутина лестницы (обе копии) |
| **2. Продажи и сводки** | `SalesSync`, возвраты, утренняя и дневная сводки, экспорт в Sheets | 3 суток параллельно, дневные сводки совпадают по билетам/заказам/сумме | — (часовая рутина пока шлёт только письма) |
| **3. Почта** | Graph OAuth, `Mailer`, аутбокс с ручным подтверждением → затем авто | 20 писем подряд без дублей и без промахов по шаблону | часовая рутина целиком |
| **4. Корзины** | `CartsPipeline`, окна тишины, потолки, статусы в UI | неделя без ложных догонов (никому, кто уже купил) | рутина догона корзин |
| **5. Справочник и цены** | редактор справочника в UI, калькулятор цены + xlsx, отказ от Apps Script как источника | справочник правится только в приложении | зависимость от Sheets |
| **6. Упаковка** | подпись + нотаризация, автозапуск через launchd, автообновление (Sparkle), бэкапы, dead man's switch | перезагрузка Mac → всё поднялось само | — |

Оценка (работа с Claude Code, календарно): фазы 0–2 — 3–4 дня, фаза 3 — 2 дня (основное
время уйдёт на регистрацию приложения в Entra ID), фазы 4–5 — 3–4 дня, фаза 6 — 1–2 дня.
Итого ≈ 2 недели с обкаткой вхолостую, из которых львиная доля — наблюдение, а не код.

## 14. Риски

| Риск | Что делаем |
|---|---|
| Mac спит / выключен | §11: питание от сети + запрет сна + догон; при жёстком требовании — VPS |
| CRM меняет формат или режет частоту | `raw_json` в базе, ретраи с backoff, троттлинг, алерт на схему, период настраивается |
| Graph-токен истёк / админ отозвал согласие | refresh в Keychain, алерт за 7 дней до истечения, фоллбэк на SMTP |
| Дубль письма клиенту | уникальный индекс `emails(kind, ref_id)` + вторичная проверка `sentItems` |
| Письма в спам | SPF/DKIM/DMARC, темп отправки, отказ от ссылок-редиректов в шаблонах |
| Потеря базы | ежедневный `VACUUM INTO` + внешняя копия; CRM остаётся восстановимым источником |
| Данные покупателей на ноутбуке | FileVault, шифрованные бэкапы, минимум хранимых полей |
| Один человек в проекте | всё в git, README с «как поднять с нуля», никакой магии в ручных шагах |

## 15. Что остаётся за Claude — и почему это уже не зависимость

Операционный цикл после миграции полностью детерминирован: опрос CRM, учёт, письма,
алерты, сводки, лестницы, расчёт цен — обычный код. Модель нужна только там, где есть
суждение:

- **оценка спроса перед закупкой** (статус продаж у организатора, вторичка, масштаб артиста,
  русскоязычная релевантность) — это поиск по интернету и вывод, а не арифметика;
- **тексты писем и описаний** — разовая работа, результат ложится в справочник.

Оба случая — по запросу, а не по расписанию. Если захочешь оставить их внутри приложения,
это делается своим ключом Anthropic API: кнопка «оценить спрос» в калькуляторе цены, которая
ходит в API напрямую. Тогда зависимость — это строчка в настройках, которую можно удалить,
а не инфраструктура, без которой ничего не работает.

## 16. Открытые вопросы

1. **Где живёт движок 24/7?** Mac, который всегда включён (вариант А), отдельный Mac mini
   (Б) или VPS с Mac-интерфейсом (В)? От ответа зависит только упаковка, но решить лучше
   до фазы 2.
2. **Google Sheets — оставляем?** Нужен ли тебе привычный лист как витрина (тогда держим
   экспорт навсегда), или всё переезжает в приложение и Apps Script отключаем?
3. **Есть ли доступ администратора Microsoft 365** (регистрация приложения в Entra ID)?
   Если нет — идём по SMTP-пути, это меняет фазу 3.
4. **Письма: ручное подтверждение навсегда или авто после обкатки?** Предлагаю: вэлком —
   авто после 20 успешных, догон корзин — ручное подтверждение дольше (там скидка и риск
   написать не тому).
